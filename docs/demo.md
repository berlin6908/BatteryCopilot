# 演示与简历说明

## 三分钟演示

[观看三分钟字幕演示（MP4）](https://github.com/berlin6908/BatteryCopilot/releases/download/v0.1.0/battery-copilot-demo.mp4)

视频展示真实应用与提前生成的 Terra 报告，含原始行、结论来源、资料缺口、演示复核意见、
刷新恢复和导出；字幕明确说明生成发生在录屏前。录屏中的复核意见不是工程师验收。
数据来自 KIproBatt v0.3.2，CC BY 4.0，作者和转换说明见
[完整署名](../data/sources/kiprobatt/ATTRIBUTION.md)。视频中的应用界面和生成报告由本项目制作。

复录需 Node、可解析的 Playwright 包、本机 Edge 与 FFmpeg；先执行 `playwright install ffmpeg`。
对独立演示数据库运行，脚本会生成真实报告并保存标为演示的复核意见：

```powershell
$env:BASE_URL = 'http://127.0.0.1:18000'
node scripts/record-demo.cjs
uv run python scripts/render-demo.py
```

字幕 MP4 与原始录屏写入 `data/runs/demo/`，仅最终 MP4 作为 GitHub Release 附件。
若录制中断且已生成报告，可设置 `DEMO_REUSE_REPORT=1` 复用同目录的模型事件与已保存报告；
已填写复核意见的报告不能再次提交复核，完整重录应生成新报告。

演示前按 README 启动服务，确认首页可列出电芯、模型已连接。选中默认样本
`FormatedCell1 · 101_tizue-ki-230306-tizue-0400-059_-STATS-.txt`。
生成耗时受本机与模型服务影响，可以提前保存一份报告，现场展示查询过程与历史恢复。

| 时间 | 操作 | 要说明的业务价值 |
| --- | --- | --- |
| 0:00–0:25 | 展示制造履历，展开注液参数 | 工程人员从一个电芯对象找到明确前驱、工序与本对象参数，减少跨文件查找。 |
| 0:25–0:55 | 点击 Cycle 1 的原始行 | 放电容量为 0.438290374336 Ah，能定位到文件第 11 行；数值、单位和来源一起展示。 |
| 0:55–1:40 | 提问并生成制造复核报告，展示工具调用 | Agent 根据问题选择履历、参数和循环查询；范围与数值读取由工具负责。 |
| 1:40–2:15 | 打开结论引用，说明缺失资料 | DryCell 是明确关系的追溯终点；缺少更上游的链接不等于制造从这里开始。测试条件与验收标准不足，不能据此判定合格或计算 SOH。 |
| 2:15–2:45 | 刷新，从「已保存报告」打开，填写复核意见并导出 | 输出成为可继续处理的资料复核报告，包含来源快照和人工意见。演示时复核人填写「演示复核人」，不冒充工程师验收。 |
| 2:45–3:00 | 展示制造评测结果及一个失败案例 | 说明固定查询对照、抽查发现的问题和修复，不只展示成功回答。 |

现场问题可以直接使用：

> 追溯当前电芯的明确前驱和制造工序，核对 Cycle 1 的充放电容量，
> 列出缺失的工艺参数与测试条件。每条结论给出来源，并说明现在能否作质量判定。

如果需要展示不同业务流程，再进入「变更复核」：选择缺资料示例，保存并分析，
补充工具卡后重新分析，逐项复核并导出。工具卡和规格是明确标注的模拟业务输入。

## 简历表述

项目名称建议：**Battery Engineering Copilot——基于制造知识图谱的工程资料复核 Agent**。

- 基于公开 KIproBatt 电芯试制数据构建制造知识图谱，将 786 份 JSON-LD 中的
  24,577 个源节点、718 个过程实例与 108 份循环统计关联，保留原始属性、单位与行级来源。
- 使用 Python、FastAPI、Neo4j、LangGraph 和 Flutter 实现单电芯履历追溯、
  参数核查与循环定位，通过五个受电芯上下文约束的工具生成引用报告，支持保存、人工复核和来源快照导出。
- 建立无资料、固定查询与 Agent 三种对照，分别检查字段正确性、预设引用覆盖、
  工具调用量及延迟；通过原始来源抽查定位参数归属与引用范围问题，并保留修复前后的运行结果。

评测数字引用[制造验证报告](manufacturing-validation.md)时，写明分母、同批次新对象范围
和是否为修复后重放。不要把公共实验室数据写成企业量产接入，也不要虚构节省工时或质量收益。

## 面试时应能解释的问题

- **Agent 做了什么？** 根据用户问题和中间证据选择下一次查询与停止时机，整理有来源的报告。
  图中的前驱、对象范围、数值和计数由确定性工具提供。
- **为什么需要图谱？** 本项目核心是对象状态、前驱参数、工序和文件之间的关系追溯。
  Neo4j 同时提供路径查询和指南检索索引，避免引入第二个数据库。
- **固定流程也能做，Agent 的价值在哪里？** 对明确循环编号等固定任务，固定流程是强对照。
  Agent 可以按问题少读资料，但会增加模型轮数；是否值得应看实际调用量、延迟和任务种类。
- **为什么不让模型直接写 Cypher？** 五个领域工具已经覆盖当前任务，并集中限定对象范围和查询语义。
- **引用存在就可信了吗？** 不能。数值对了仍可能归属对象错误；单个文件参数也不能证明整条履历缺失。
  因而同时保留来源抽查和人工复核。
- **为什么没有微调和多 Agent？** 当前可验证的问题是取证、来源范围和流程交付，现有单 Agent 已能完成。
  尚无独立标注的训练资料证明增加这些组件能改善结果。

实现路径和取舍详见[架构说明](architecture.md)。
